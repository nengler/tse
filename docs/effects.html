tseAuthoring guide and reference

Effects and audio

State is for what lasts. A burst of dust where you landed, or a sound, happens at a moment and then plays out. For those, you make a store once, mount its renderer once, and call it from anywhere, as with a toast library. There is no useEffect.

  • A burst belongs to the layer, so it plays out even if whoever asked has left. With no layer mounted, it is counted but not drawn.
  • A preset is <Particles>'s props except rate, emitting and space.
  • A burst's color and endColor replace the preset's for that burst only, so one preset can make every enemy's death puff in that enemy's colour. One not given stays the preset's; a preset with no endColor keeps a given color throughout.
  • A sound with once: true plays at most once a step however many components ask for it: twenty towers firing together make one sound.
  • Continuous effects (a trail while dashing) stay in JSX: <Particles emitting={dashing} space="world" />.

Motion: springs and tweens

  • Each follows its target: change the target (from state or props) and the value moves to it. Both start at their first target, without moving.
  • useSpring is set by duration (about the seconds it takes to settle, default 0.5) and bounce (0, the default, for no overshoot, up to just under 1 for a lot of it). A new target keeps the speed it had, so it turns round smoothly.
  • useTween takes duration (default 0.25) and ease: linear, inQuad, outQuad, inOutQuad, inCubic, outCubic (the default), inOutCubic, inSine, outSine, inOutSine, inBack, outBack, outElastic, outBounce, or a function from a .ts file. A new target starts again from where it is.
  • They step in the component's useUpdate: they follow the fixed step, freeze and replays, render only while moving, and keep their place through a hot reload. They also stop while <Game paused> is on, so a pause menu does not animate.
  • Each takes a number: a point is two springs, one for each axis. In plain code, stepSpring and stepTween (from @tsengine/runtime) take points too.
  • opacity={…} fades any element and what is in it; see Position and drawing order.

Music and fades

Freeze frames, shake, squash

Kite also uses <Particles> directly, for room-wide drifting dust (width, height, prewarm, space="world") and dash sparks (emitting={body.state === "dash"}). Its dash trail is a list of ghost Sprites in state, with falling opacity.

  • freeze(steps), called in a handler or in plain TypeScript (Kite calls it from playEvents), skips every useUpdate for that many steps (a hit, a dash). useInput keeps running, and a press during the freeze is kept for the first step after.
  • useShake() and useSquash() are state: see Custom hooks.

Layers, light and blend modes

A <Layer> draws its children off screen, into a picture the size of the screen, and then lays that picture over what is under it with a blend mode. That is how a cave goes dark and a lantern lights it again: a layer of near-black, multiplied over the world, with lights added into it where they shine.

<Lighting ambient> is a <Layer blend="multiply" childBlend="add" clear={ambient}> set up as a light map, and <Light radius color intensity> a soft disc of colour falling off smoothly to nothing; lights that overlap add up. A light needs no image. Anything else may go in the layer too: a sprite drawn in an add layer is a light of its shape.

  • blend is how the layer meets what is under it: "normal" paints over; "multiply" shades (white leaves it as it is, black makes it black); "add" brightens; "screen" brightens but never past white.
  • childBlend is how each child is drawn onto the layer itself: "add" makes two overlapping lights brighter than one.
  • clear is what the layer holds before its children are drawn, every frame (transparent by default): the darkness of a light map.
  • opacity fades the whole layer, and an opacity above it applies to the layer as a whole, once.
  • It is drawn through the same camera as the world (or the HUD's view, inside a <Hud>), so children are placed in world coordinates as usual. It covers the screen (the game's canvas under a <Screen>).
  • Inside a layer, children are drawn in tree order: a z there is ignored, and the layer as a whole is drawn at its own z. Layers nest four deep.
  • Bramble's cave is the example: games/bramble/src/Play.tsx, the lantern, the items still lying there (glowsOf in rules/view.ts) and the wisps as lights, and its picture in stories/screenshots/Play/Cave.png.
  • Lights do not cast shadows: walls do not block them.

Shaders

A layer can send each of its pixels through a shader as it is laid over: a flicker, a vignette, a ripple, a palette. The shader is a file under assets/ holding one function, effect, in GLSL; the engine wraps it for the platform it runs on.

  • effect is given image (the layer: read it with texture(image, uv)), pixel (where this pixel is, in screen pixels from the top left), resolution (the screen's size), time (the game's seconds, so a replay looks the same) and params (eight numbers from params={[…]}, the rest 0). What it returns is the pixel, which the layer's blend mode and opacity then use.
  • A missing file is a build error, with the nearest name, as a missing image is. GLSL that does not compile is reported when the game starts, with the compiler's message and a line in your file, and the layer is drawn without it.
  • The software renderer that tests, previews and tse screenshot use runs no shaders: it draws the layer as it is and says so once. tse screenshot --gpu shows them.

Shaders on a sprite

A <Sprite> or <AnimatedSprite> can send its own pixels through a shader as it is drawn, with the same kind of file. A layer's shader sees the whole screen; a sprite's sees the sprite, and knows how it is turned. That is what lighting needs when the light stays put and the sprite rolls: a ball lit from the top right of the screen stays lit there however it spins.

  • Besides what a layer's shader is given, effect gets region (the part of image drawn, as x, y, width and height in its pixels: one frame of a sheet), turn and lookup.
  • turn takes a direction in the image to the direction it is drawn on the screen (y down), with the sprite's rotation, its flips and the camera's. It never stretches, so transpose(turn) takes it back: a direction on the screen, found in the image.
  • lookup is a second image, from lookup="ramps.png": a colour table, read with texture or texelFetch, so shading can step through colours you chose (warmer toward the light, cooler away from it) instead of only brightening and darkening. Without one it is a white pixel.
  • time is 0 on a sprite. For one that moves with time, pass it in: const time = useTime(); and params={[time]}.
  • Each shaded sprite is drawn on its own, so shade tens of sprites this way, not thousands. A missing file is a build error, as for a layer, and the software renderer draws the sprite as it is.

Input actions and timing

Named actions

Name actions once, and every input.pressed / down / released then accepts a name as well as a key. Rebinding changes that one list.

  • down: any key held. pressed: one went down this step. released: one went up with none still held.
  • An unknown name warns once and lists the actions. For rebinding at run time, see Saved data. There are no analog axes.
  • Gamepad: the first pad's buttons and four directions are keys (see key names). gamepadDeadzone on <Game> sets the stick threshold.

Forgiving input: buffers, coyote time, clicks a button took

  • input.pressedWithin(key, seconds): the key (or an action's key) went down within the last seconds of game time, this step included, and the press was not taken. pressedWithin(key, 0) is pressed(key). Game time is the steps' dt, so under fixedStep a window is whole steps and a replay repeats it.
  • input.consumePress(key) takes the key's last press (each of an action's keys), so pressedWithin stops seeing it. pressed is not changed.
  • grace(active, left, dt, seconds) returns seconds while active, then counts down to 0: keep it in a field and pass it back each step. It is a plain function, so it also works in a rules file.
  • input.pressHandled is true on the step that sees a left click that a <Pointer>, <Button> or other pressable took. input.pressed("MouseLeft") is still true then: check both.

Who hears the keys: inert and modal

Input is polled, so every useInput sees every key. Two props of <Entity>, <Flex> and <Hud> decide which subtrees hear it, as in HTML, so a component does not have to guard itself with an if (paused) return.

  • inert is the HTML attribute. In the subtree, useInput and useUpdate get no keys pressed or held, and pointers and buttons cannot be pressed, hovered, focused or reached by their pressKey. It still updates, draws and collides.
  • modal is a <dialog> opened with showModal(): everything outside it is inert, its ancestors too, and the focus stays among its buttons. If several are mounted, the one mounted last takes the input; when it goes, the one below has it again.
  • A component passes them on as it would any prop, at its root: function Menu({ inert }: MenuProps) { return <Entity inert={inert}>…</Entity>; }, then <Menu inert={capturing} />. (A state field cannot be named inert or modal: they are the root's.)
  • It decides who hears input, not who updates: to stop the world stepping while a pause menu shows, give the root <Game paused={paused}> (below).
  • A modal mounted during a step hears keys from the next step, so the press that opened it does not reach it. Bramble's "press a key" prompt (KeyPrompt.tsx) is a modal with no children that takes the next key.

Fixed timestep

  • useUpdate runs at a fixed rate with dt = 1 / rate. A frame runs no step, one, or several (at most 8; leftover time is dropped). Drawing stays once per frame.
  • Each frame is drawn between the last two steps, by how far it is into the next one (interpolate, on by default), so a 60-step game moves smoothly on a 120 Hz or 144 Hz screen. Positions, rotations, scales and the camera's follow and slide are blended for drawing only: useUpdate, collisions and saves see whole steps. It draws up to one step behind. Something that moves more than 64 pixels in one step (a respawn, a door) is drawn where it lands, not slid there. <Game interpolate={false}> draws the latest step instead; a hidden window (tests, tse screenshot) does that by default.
  • A tap between two steps is not lost: the next step sees it as pressed and released.
  • The fixed step is off by default. Without it, there is one update per frame, with the frame's own time.

Timers: after and every

  • You call them as statements in a handler, as you would setTimeout in React. The function you pass is a handler too: it writes state, calls actions, plays sounds.
  • A timer is the component's: it is cancelled when the component unmounts, so it never sets state on one that is gone.
  • after and every return the timer's id (1, 2, 3… for the component, never 0, so 0 in state means none). cancelTimer(id) stops that one timer and leaves the others; an id that is done, or 0, is ignored.
  • They count game time in the update phase: they follow the fixed step and replay, and stop during freeze and <Game paused>.
  • Choosing between a timer and state: a timer is code, so it is not saved and a hot reload drops it (the log says so). Use one for what is only for the eye: a flash, a blink, a beat before a title appears. A delay that is part of the game (a few seconds of safety after a hit, a slow) is state that counts down in useUpdate, or a time it ends at kept in state: it is then saved, reloaded and tested like any state.

Cutscenes: sequences

A cutscene is a list of steps run one after another as game time passes: a sequence, written as data in a .ts file. A component keeps it in a field and steps it from useUpdate; while it runs, the component can hold the world still.

  • Steps: wait(seconds), call(fn), waitFor(() => done) (the player closing a dialogue), tween(seconds, set, ease) (calls set with 0 to 1, ending on 1; eases linear, easeIn, easeOut, easeInOut), parallel([…]), and sequence([…]) itself, which nests.
  • step(dt) returns true while there is more to run. Time left over when a step ends goes to the next, so a sequence takes what its steps add up to, whatever the step size; under the fixed timestep it plays the same every time, and replays.
  • Start the field from a function (noCutscene()), not null: the compiler lets a component call the methods of an object a function made for it, and types the field from what that function returns.
  • position is where it is, as plain data, and restore(position) carries on from it: a save can keep a cutscene half played. reset() starts it over.
  • A test steps one without the engine: const s = caveIntro(…); s.step(1);. A replay that crosses a cutscene waits it out (Bramble's test/fullrun.ts).

Fast-forward and pause

  • timeScale={2} runs two steps a frame, each with the same dt: the game plays exactly as at 1, twice as fast, and a replay is the same at either speed.
  • paused stops every useUpdate. useInput, presses, pressKey and the focus still work, so the pause menu's buttons unpause it.
  • Unlike the other <Game> settings, these two are read every frame, so they may be state.

Seeing inside a running game

  • Under tse dev, F1 in the window (<Game overlayKey> to change it) shows the layout overlay. It outlines every <Flex> and its padding, every collider (a colour per layer) and every pointer, and labels the box under the mouse with the components it is in, its size and what sized it (width grow). A packaged game never has it.
  • tse dev also prints the address of the inspector (inspector: http://127.0.0.1:…/): open it in a browser to see the tree by component, as React DevTools shows it; the selected component's state, props, the game-state paths it reads and how many times it has rendered; and each game state with its last actions and what each one changed, as Redux DevTools shows them.
  • In the inspector you can change a state value or a game-state leaf by typing a JSON value. The change shows on the next render. An edit is not input, so a replay does not repeat it; the log says so each time.
  • The inspector's profile button times every component while the game runs. Once a second it shows a table of milliseconds a frame: for each component (by name, with how many there are) its input, update and render time and renders a frame, the slowest first, and above it the frame's phases (steps, collisions, building the frame, drawing). A row over a millisecond is red. Timing costs a little, so it is on only while the button is; in a test or a tool, startProfiling() from @tsengine/runtime gives the same report (profiler.take()).

Rewind

Under tse dev the game records every frame's input and takes a snapshot every second, for the last five minutes. Go back to the moment something went wrong, fix the code, and watch the same moment again.

  • F2 pauses. ← and → go back and on a frame, ↑ and ↓ a second; a bar over the game shows where you are. F2 again plays on from there with live input, and the recorded future is dropped. The inspector's page has the same timeline, with a slider.
  • Going to a frame restores the snapshot before it and plays the recorded input again to it, silently and without drawing: under a tenth of a second.
  • If you save a file while paused, the game is reloaded and the same input is played again with the new code, to the same frame, so you see the moment with the fix.
  • F4 saves the moment (from the snapshot before the paused frame to it) to moments/. A test plays it again with replayMoment from @tsengine/player, so the bug becomes a replay test.
  • It relies on the game being a function of its input. Each frame's state is hashed as it is played; when a replay differs from the recording (Math.random or Date.now in the game, a timer used for gameplay), rewind names the first frame that differs, in the log, on the bar and on the page.

Testing without a window

  • npm run check:kite (or check:<game>) compiles, type-checks, runs tests and replays the game headless.
  • Input scripts: right*30, jump, right*20+dash. Items run in order, + starts terms together, name*N holds N frames, a bare name taps, _ waits. A key stays held until the script changes it, so right, right is one press held for two steps, and right, _, right is two presses. A name that is neither a key nor an action throws, listing the actions. click@Play taps what is labelled Play (the middle of the topmost thing that can be pressed and holds that text, as it is drawn when the frame comes up), so a script does not break when a button moves; click@120,64 taps a point. runScript steps a game and returns what you observe. playGame(gameConfig, { bindings }) plays one a piece at a time: game.input("Enter, _*5, Space") runs a script, and game.stepUntil(() => run().phase === "pick") waits for the game instead of counting frames, so a test does not break the day something takes a little longer (it throws after maxSteps, default 3600). A game exports bindings ({ jump: ["Z"], … }) so scripts can use action names.
  • tse screenshot <game> --script "right*30" --at 0,29 renders chosen steps to PNG through the software renderer (needs npm run native:build:headless). It compiles the game first, as tse check does, so a shot always shows the current source. If the game does not compile, it prints the errors and writes no shot.
  • For motion, --every N --sheet name writes every Nth step and one contact sheet of them; --from and --to keep it to one stretch of a long run.
  • --at counts back from the end with a negative number, and last is the last step: --at 0,-30,last. A shot of how a script ends does not need its frames counted.
  • --setup file.ts names a module whose default export (player, step) => void is called before each step. Use it to put the game where the shot needs it (a later level, a full jar) without playing there; findComponent from @tsengine/testing reaches a component's state.
  • A shot starts with no saved data and keeps none, so it looks the same whatever was played before and the player's saves are left alone. --saves uses the real ones.
  • --gpu draws them with the desktop build on OpenGL instead, as a player's window does, so what a driver or a shader does shows. It needs npm run native:build; without a display it runs itself under xvfb-run, which Mesa's software OpenGL draws for.
  • --compare refs/ checks each frame against refs/step-<n>.png and fails if one differs; --tolerance 64 lets a channel differ by that much (two Mesa versions do), and --update writes the references. npm run check:gpu does this for the demo and Kite, and CI runs it.

Testing one component: @tsengine/testing

As React Testing Library tests one React component, render mounts one compiled component in a headless world, and the test steps it, presses keys, reports collisions and presses, and reads what it holds and what it would draw. A component that owns its logic is then as easy to test as a rule.

  • render(Component, props, { tilemaps, controls, dt, collisions, keepGameState }): the game state is put back to its start, the maps are registered, and the component is mounted. So a test sets up the game state after render, through its actions, or passes keepGameState: true to keep what it set before. Without collisions: true colliders never meet by themselves: a test reports the contacts it wants with collide. With collisions: true each step finds its own contacts, as the player does, so a component whose children collide (a battle's enemies and shots) is tested whole.
  • place({ tag, data, x, y, width, height, onReceive }) puts another collider in the world, for the component to find or touch (an enemy near a tower); with onReceive the test sees each value the component sends to it. remove(collider) takes it out.
  • send(tag, { x, y, radius }, value) (or a t.world.nearby(…) result in place of the circle) hands a value to the component's colliders of that tag, as another component's send would, and delivers it to their onReceive at once, without a step.
  • step(n) runs steps with nothing pressed; input("down, _, confirm") runs an input script, through the game's controls when given.
  • stepUntil(() => !play.s.active, { maxSteps }) runs steps until the condition holds (asked before the first and after each) and returns how many it ran; not done within maxSteps (default 3600) it throws, or with throws: false returns maxSteps, for a balance run where a wave that never ends is a result to record.
  • collide(tagOrCollider, { tag, data, width, height }, times) and separate(…) report contacts; press(pointerOrName) clicks a pressable in its middle; setProps(props) gives new props; unmount() runs its unmount handlers.
  • state(component?) is a component's state by the names in its source; texts() the words of every <Text>; find(nameOrClass) and findAll search the tree.
  • Outside render, a whole-game test, a replay check or a balance tool reads the running game the same way: findComponent(Play) (or findComponent("Hero")) is the component in the game's tree, findComponents every match, and componentState(component) its state by the names in its source, all from @tsengine/testing.

Previews: one component on its own

As Storybook shows one React component with given props, tse preview shows one component of the game, without playing to where it appears. A stories/ folder beside test/ holds a file for each component: its default export says how it is shown, and every other export is a story, its props.

  • stories(Component, { size, origin, scale, background, wrap }): the screen the component is drawn on (size, in game pixels), where its own (0, 0) sits on it (origin, default the top left), how many times larger a screenshot is (scale, default 4), and wrap to put it inside something it needs, a Provider or a Flex that gives it a width. It is drawn with the game's own <Game> look: background, assets, font, text size and colour, controls.
  • story(props, { setup, input }) for a story that sets game state first (every game state is put back to its start before setup) or plays an input script before it is looked at. A plain object is props only. Stories are listed by name.
  • tse preview opens a window on the first story, with hot reload: save the component or the stories file and it changes in place. F5 and F6 go to the previous and next story; --story SidePanel (or SidePanel/Build) starts at one.
  • tse preview --screenshot stores a PNG of every story in stories/screenshots/; commit them. tse check then renders every story again and fails on a picture that changed, on a story with no picture, and on a picture whose story is gone, and says where the new pictures are. When the change is meant, store them again. This needs the headless libtse, which @tsengine/native ships; without it the check says it did not compare.

Hearth's stories found the build menu's 2 MORTAR 80 a few pixels wider than the side panel, which the game showed cut off at the window's edge.

Saved data and settings

A save and the player's settings are kept between runs in the game's folder in the user's data directory ($XDG_DATA_HOME/<id>, ~/.local/share/<id>, or $TSE_DATA_DIR in tests). Name the folder with the id prop of <Game> (a literal: letters, digits, _, -); without it nothing is kept.

  • With tree: true, component state is saved too: an enemy that keeps its own hp in useMutable keeps it in the save. On load, apply runs first; once the tree it builds has settled, each component takes its saved state back, found by its path from the root, and a list item by its key (so an enemy removed before the save is loaded does not hand its state to the next one). Values that are not plain data (a function, a body) are left out, said once.
  • A save is stored as JSON, { version, data } (and tree with tree: true). A file that does not parse is said once and read as no save; a save from a newer version than the game is refused with a message; migrate steps run in order up to the current version.
  • Settings are applied when the game starts, before the first frame, and on each set: music and effects are the two volume groups (setVolume("music", v) multiplies every <Music>; effects every sound), fullscreen switches the window, bindings goes to controls.load. Other settings are the game's own.
  • settings and controls are not state a component reads, so settings.subscribe(fn) (after each set, reset and reload, once applied) and controls.subscribe(fn) (after each bind, reset and load) say when they change; both return the function that stops it. A component shows them with useStore(settings, read), the counterpart of React's useSyncExternalStore. read is a function from a .ts file that returns what to show. It runs at mount and on each notification, the component renders only when the data it returns differs, and the subscription ends when the component goes (Bramble's Settings.tsx). Underneath it is useMount returning the subscription's cleanup, which a component can also write itself. If several screens show a setting, mirror it into the game state from a .ts module instead.
  • To rebind, use controls.bind("jump", ["Space"]) (false for an unknown action or a key that is not a key name), controls.reset(), controls.toJSON(), controls.load(data) (ignores unknown actions and keys). The change applies at once. input.lastPressed() is the first key pressed this step, or undefined; it is how you write "press a key for Jump" (const key = input.lastPressed(); if (key !== undefined) bindKey(action, key);).
  • In a runtime test, call setStorage(createMemoryStorage()); new RecordingBackend({ storage: { save: "…" } }) starts a replay from a save, and backend.stored shows what was written.
