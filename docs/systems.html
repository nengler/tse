tseAuthoring guide and reference

Collisions and presses

There is no physics: the player notices when boxes start and stop touching and calls your callbacks. A Collider is an invisible box with its top-left at the object's position. Pair it with a Shape to see it.

ConceptMeaning
other.tagThe other collider's tag ("" when none). Tells apart colliders on one prefab.
other.ownerThe name of the nearest <Entity name> at or above the other collider, or its component's class name. Tells apart prefabs.
other.dataWhat the other collider's data prop holds: <Collider tag="coin" data={{ value }} /> lets the player read other.data.value. Typed by tag once the game declares ColliderData (below); unknown until then.
layer / hitsA pair is tested only when each side's hits allows the other's layer. Use them to skip pairs cheaply (bullets ignore bullets). Unrelated to tag.
onCollisionExitFires once when a touching pair separates, or when the other leaves the world. It does not fire for a collider that itself left.
In a <Hud>Colliders never touch anything.

Shapes

A collider is a box unless it says otherwise. shape="circle" is the circle inside its box (centred, half the shorter side across); shape="polygon" with points={[0, 16, 16, 16, 16, 0]} is a convex polygon in its own pixels, inside its box (a ramp, a blade). Pairs are found by their boxes first. A pair in which either collider has a shape is then tested exactly, rotated with its objects, so two round coins whose boxes meet at the corners do not touch. A pair of plain boxes is tested as upright boxes. useBody's touching and overlapping see a shape too. A body is always a box, and a solid collider stops bodies at its box whatever its shape, so there are no slopes.

On other, handlers can read tag, owner and data and nothing else. To type data, declare once, in any .ts file, what each tag carries; comparing other.tag then narrows other.data:

Once it is declared, every tag a game compares must be in it.

Collider or tile? Contacts are found after every step, and whatever a callback changes is rendered before the next step and drawn in the same frame. A callback still runs after the step's useUpdate, though, so code that must know mid-step (movement against walls, a precise death) reads tiles instead: Kite reads spikes and exits as tiles inside its movement step, and uses Collider for the optional gem pickup.

Finding and hitting things in an area: nearby and send

A component has no handle on another, so a tower cannot call an enemy. It asks the colliders instead. nearby(tag, x, y, radius) lists the colliders with that tag whose boxes come within a circle (a real circle, not a square), nearest first. Each entry has the collider's tag, owner and data, the middle of its box (x, y) and its distance (0 inside the box). send(tag, where, value) hands value to the onReceive of every collider with that tag in a circle ({ x, y, radius }), or to the single collider a nearby result describes. Call both from a handler (useUpdate, useInput, a callback prop). Neither includes the colliders that the calling component draws itself, so a send never reaches its sender. A move that should also affect its user (a buff on everyone in range, the caster included) applies that part to the caster directly.

RuleMeaning
When it arrivesAt the end of the step's update phase: after every useUpdate and timer, before the step renders and before its collisions are found. So it lands in the step it was sent, and what a receiver changes is drawn that step.
In what orderThe order values were sent (handlers run in tree order, so that order repeats), each send's receivers nearest first. A value sent from an onReceive is delivered later in the same phase; one sent from a collision callback, at the end of the next step's update phase. Replays and the two players give the same result.
Where things areBoxes are where they were when the step's updates began, as for useBody. A nearby result is good for its step: keep an id from its data, not the result, across steps. A receiver that left the world before delivery hears nothing.
TypesDeclare what each tag can be sent beside ColliderData: interface ColliderMessages { enemy: Blast }. Then send("enemy", …, value) and onReceive's value are typed by the tag; undeclared, the value is unknown.

Use send in place of a collider that lives for one step only to carry a message (a blast's collider whose data every enemy it touches checks). There is no extra collider and no step of delay, and the receiver does not have to check whether the blast was meant for it.

Pointer presses

A left click goes to the topmost Pointer or Flex onPress under the mouse. HUD buttons work however the camera moves.

Placing things

Anything laid out in rows or columns is a <Flex>, wherever it is (a menu over the world, a row of hearts, an inventory, a panel in a <Hud>). Anything the game moves (a character, a coin, a shot) is placed with x and y from its state.

x, y, z, rotation, scaleX, scaleY, global and opacity are props of every built-in that can be placed: <Sprite image="coin.png" x={spot.x} y={spot.y} />. A component takes none of them, since a component may declare an x of its own. To place one, wrap it in an <Entity>, <Entity x={40} y={8}><Coin /></Entity>, or give it x and y props that it puts on its root (see Position and drawing order).

Rows and columns: Flex

A <Flex> lays out its children in a row or column, with flexbox props and Clay-style sizing. A child's own x and y still offset it within its slot. Only a Flex is resized; Sprite, Shape and Text keep their size.

Size valueMeaning
"fit" (default)The children plus padding and gaps.
"grow"The fit size plus a share of the parent's free space.
120Fixed pixels.
"50%"A percentage of the parent's inner size.

A Flex can be styled with props, which are checked like the layout ones: background, borderWidth and borderColor (the border is drawn inside the edge and takes room like padding), and borderRadius. hoverBackground and hoverBorderColor are drawn while the mouse is over the box, and focusBackground and focusBorderColor while it has the focus; hover wins when both apply. pressedBackground and pressedBorderColor are drawn while the mouse button is held on the box, and disabled (with disabledBackground and disabledBorderColor) switches a button off: no press, key or focus reaches it, and it shows only its disabled colours. Over one another the states go plain, focus, hover, pressed, and disabled over all. They change colours only, so nothing moves when the mouse does, and the component does not render again. Give the box a transition (seconds) and its colours fade between states instead of snapping; a fade that is cut short reverses from wherever it had reached. A box with a hover prop takes the mouse but lets a press through to what is under it, unless it has an onPress.

<Slider> and <Toggle> are two controls that are Flex boxes with parts drawn in them, so they are sized, laid out, clipped, faded, disabled and styled like any other. A slider is <Slider value={s.volume} min={0} max={10} step={1} onChange={(v) => { s.volume = v; }} />: a press puts the thumb under the mouse, a drag moves it (even once the mouse has left the box), and when it has the focus the left and right keys move it one step (a twentieth of the range with no step) while up and down move the focus on. The track is its background, so it takes a border, a radius, an image and a colour for each state; fillColor is the part left of the thumb. A toggle is <Toggle checked={s.sound} onChange={(on) => { s.sound = on; }} />: a press, the confirm key or its pressKey flips it. Each moves its own value and then calls onChange with the new one, only when it is different, so value and checked give the starting value and any value you set later. Both take the focus by default.

<Button> and <Menu> are the two pieces most screens need. A button is a Flex that takes the focus and has a look for each state, its label as children; any Flex prop replaces the default look. A menu is a column whose focusable children are its items: while one of them has the focus, up and down move it only among them, wrapping round at the ends (loop={false} stops there), confirm presses the focused one, and back (Escape or PadB without a back action) calls onBack. autoFocus says which item starts with the focus. onAdjust on any focusable box hears left and right while it has the focus (-1 or 1), for a row that changes a value in place; the focus stays. When a modal opens over a menu its focus is put aside, and given back when the modal closes. A component of your own called Button or Menu is still yours: a name declared or imported in a file shadows the built-in, unless the file imports the built-in too.

wrap lets a row break into lines: a child that will not fit in what is left of a line starts the next one. Give the box a width (width={120}, "50%" or "grow"); with only a fit size it is one line. Lines stack downward, each as tall as its tallest child, with rowGap between lines and columnGap between the children of a line (both default to gap). justifyContent places the children of each line on its own, so a short last line is not spread like a full one, and alignItems places each child inside its line's height. Children keep their size (a "grow" child takes only its content's size, and none shrink); one wider than the box is alone on a line and sticks out. Only rows wrap. To scroll a long grid, put it in a direction="column" scroll box with width="grow" on the grid, so its width is the box's and it wraps there instead of running off to the side.

opacity fades a box and everything in it, from 1 (as it is) to 0 (gone): <Flex opacity={open ? 1 : 0} transition={0.2}> is a panel that fades in and out. It multiplies into every colour, sprite and piece of text under the box, so a faded box inside a faded box is at the product of the two. Each part is drawn at that opacity by itself and not flattened into one picture first, so where parts overlap (a dark button on a panel) one shows through the other while the box is part way, and a text outline, whose copies overlap, fades more slowly than the rest. At 0 nothing is drawn, but the box is still laid out and still takes the mouse; switch it disabled or take it out of the tree if it should not.

backgroundImage draws a picture behind the children, over the background colour, cut into nine by slice: the four corners keep their size, the four edges stretch along one side and the middle along both, so one small image skins a panel or a button at any size. The four sides can differ (sliceTop, sliceRight, sliceBottom, sliceLeft). hoverBackgroundImage, pressedBackgroundImage, focusBackgroundImage and disabledBackgroundImage swap the picture by state like the colours do. Edges and middle are stretched, not tiled, and with no smoothing the pixels stay crisp; a box smaller than its corners shrinks them together. The name is checked against the assets folder when you build.

overflow says what happens to children that stick out of a box: "visible" (the default) draws them outside it, "hidden" clips them to it, and "scroll" clips them and lets the mouse wheel or a drag move them. A scroll box needs a size smaller than its content (a fixed height, or a maxHeight); its children keep their size instead of shrinking to fit. A notch of the wheel moves it 32 pixels, the box under the mouse takes it, and one at its end hands it to the scroll box around it. A drag scrolls it as a finger scrolls a page: once the pointer has moved 6 pixels from where it was pressed, the content follows it. A touch is the left mouse button, so a mouse drags it too. Over a box with something to scroll, a press is heard when the button is let go, and not at all if the drag scrolled: a drag on a row of a list, or on a card whose text scrolls, scrolls without pressing it. Everywhere else a press is heard as it goes down. A drag that begins on a box that takes drags itself, such as a <Slider> or one with onDrag, is that box's and does not scroll. scrollX and scrollY are where the content starts and what the wheel changes; set the prop to jump there (clamped to the content, so scrollY={9999} keeps a chat log at its end). A child cut off by a clip cannot be pressed or hovered where it is cut off. A clip stops at the inside of the box's border, so content never paints over it, and is the rectangle around the box, so one that is rotated is clipped to the rectangle that holds it. A scroll box shows a thin bar along each axis that overflows, as long as the box is to its content as the bar is to the box (scrollbar={false} hides it; scrollbarColor and scrollbarWidth style it). When the focus moves to something inside a scroll box, such as the next item of a long <Menu>, the box scrolls just enough to show it.

float takes a box out of the flow and attaches it to a point of its parent (anchor, to, offsetX, offsetY): tooltips, badges. Use z to draw it on top.

left, right, top and bottom pin a box to its parent's edges, as they do an absolutely placed box in CSS: each is the gap between that edge of the parent and the same edge of the box, and giving any of them takes the box out of the flow. <Flex right={16} bottom={8}> sits in the parent's bottom right corner whatever size the parent is. With both edges of an axis and no size on it, the box stretches between them (left={0} right={0} is a bar across). An axis with neither is placed by anchor, to and the offset. To pin a <Text> or a <Sprite>, put it in a pinned <Flex>. A pinned box whose parent is not a <Flex> is pinned to the game's area, so <Flex right={12} top={12}> at the top of a screen is a panel in its corner.

<Tooltip> is a floating box that shows only while the mouse is over the box it is in, or that box has the focus. Put it among the box's children; it sits above its parent by default (anchor and to move it), draws over what is near it, and takes no space. Its parent takes the mouse for it, so a plain <Flex> gets one too. show forces it on or off.

<TextInput> is a one-line text field. Give it the focus (a click, or the arrows) and type: the characters the keyboard makes go in at the end, with the system's key repeat, Backspace takes the last one off, and Enter calls onSubmit. Keep the text in state with value and onChange, as with a React input; what onChange writes back is what the field shows, so it can change or refuse what is typed. While a field has the focus, letters do not trigger the game's confirm and back actions or a pressKey: only the arrows, Enter and Escape move or leave it. A game's own useInput still sees the keys; check input.typed, the characters typed this step, if it needs to.

Screen, Hud and camera

The shape of a game root

Screen: fixed resolution

fitBehaviour
"integer" (default)Largest whole-number scale that fits. Every game pixel is the same size. Bars fill the rest with border.
"contain"Largest scale that fits, fractional allowed.
"stretch"Each axis scaled on its own to fill the window.
"expand"Like "integer", but the game is widened to the window's shape. A wide window shows more world instead of bars. Lay out with grow and percentages, not fixed x positions.

Only the root <Screen> counts; it takes no x or y. Everything inside is in game pixels. Without one, coordinates are window pixels.

<Text> can keep itself readable over a busy picture. shadow="black" draws the text again a pixel right and down in that colour (shadowX and shadowY move it); outline="black" draws it in that colour at every pixel around it, outlineWidth pixels thick (1 to 3). Both work with the built-in font and with bitmap fonts and turn and scale with the text. Used together, the shadow falls from the outlined shape. They take no room in a layout, so leave padding for them, and use opaque colours: a see-through outline shows through where its copies overlap.

Built-in fonts

The engine has pixel fonts built in, so a game at a small resolution needs no font file: give font a tse: name on a <Text>, or on <Game> for every text. Each is drawn at its own height unless the text has a size (use a whole multiple of the line to keep pixels square). Their letters keep their own widths, and their digits share one width, so a score does not shift as it counts. Try several: tse preview games/demo shows each one on a game screen at 320 × 180, 480 × 270 and 640 × 360.

Hud

A layer drawn after the world that ignores the camera. Coordinates are screen pixels (game pixels under a Screen), top-left 0, 0. Put it directly in the game's root. A <Fade> goes here too.

Camera

  • The camera follows its children: <Camera><Player /></Camera> keeps the view on the player (several children: their middle; none: it stays put).
  • Children are placed as if the camera were not there. Its own x and y are an offset from the followed point.
  • zoom: 2 draws everything twice as large; must be positive.
  • bounds={[x, y, w, h]} keeps the view inside a world area. slide={0.4} eases to new bounds (a room change) instead of jumping.
  • shake={shake} takes a value from useShake().
  • Only the first camera counts. With none, the origin is the window's top-left.

Screens: Router and Route

A Router shows one Route at a time. Only the shown route is in the world.

Transition fieldMeaning
fromX, fromY, toX, toYWhere the screen being left or entered is, as an offset from its place.
fromVisible, toVisibleWhether each is drawn (and can be pressed). Default true.
cover0 to 1: how covered the whole screen is by coverColor. A fade through a colour.
  • Both screens are in the world during a transition. Without transition, screens switch at once.
  • A route's components are made when it comes and dropped when it goes, so each visit starts fresh (as with React Router). keepAlive keeps them and their state.
  • useMount and useUnmount in a screen mean "the screen came" and "the screen went".
  • The function may also take the two route names: (progress, from, to).

Tilemaps and movement

A <Tilemap> draws a Tiled map with no game object per tile. The same data is the solid grid your movement code asks about, so what is drawn and what blocks cannot disagree.

Moving a component: useBody

A component that moves and is stopped by walls keeps a body: a box that moves a pixel at a time and is stopped by the solid tiles of a <Tilemap solid> (tiles with the Tiled property solid) and by every <Collider solid>, and says what it hit in the same step. A collider's onCollisionEnter runs after the step's update, a step late for movement; a body does not wait.

  • x and y are state, in the component's parent's space (where an <Entity x y> around it would put it), so the component renders where the body is.
  • move(dx, dy) moves x first, then y, carrying fractions to the next move, and returns { left, right, up, down, tags }: the sides it was stopped on and the tags of what stopped it ("tile" for a tile).
  • touching(tag): whether a collider with that tag overlaps the body now. The component's own colliders do not count.
  • blocked(dx, dy): whether something solid is where a move by (dx, dy) would put the body, without moving it. blocked(0, 1) is standing on the ground (a body standing still is not stopped by anything, so its last move says nothing of the floor); blocked(facing, 0) is a wall to jump off. In a handler, x and y are where the body is now, after any move earlier in the step; render draws it where the step left it.
  • overlapping(tag): every collider with that tag overlapping the body now, as contacts with their data (typed by tag through ColliderData). A tower that never moves keeps a body as big as its reach to ask which enemies are near: pickTarget(overlapping("enemy").map((e) => e.data)). It sees the colliders where they were when the step's updates began.
  • Bodies move in the order their components update, each against the world as it is at that moment. Others see a body through a <Collider> the component draws at its position.

Balls that pile up: useBall

A body is moved by its own component. Things that push each other, such as fruit piling up in a jar, marbles or a ball pit, are balls: circles the world steps together, once a step, before the step's updates. They fall under their gravity, push each other apart (the lighter one further) and are stopped by every <Collider solid> and the solid tiles of a <Tilemap solid>. A pile is a list of components that each call useBall.

  • x and y are the centre, as state, in the component's parent's space; they are copied from the ball each step, so the component renders where the ball is.
  • Options: radius; gravity (pixels per second per second, downwards, default 0); gravityX (the same to the right, default 0: a tilted table, wind; setGravityX(sideways) changes it, as does a second argument to setGravity); mass (default the radius squared); friction (how much of its sliding it loses each substep it is pressed against a solid, default 0.1); drag (how much of its speed it loses each second, default 0.2); pinned (start held in place, default false); tag and data, which other balls see.
  • contacts(tag): the balls with that tag touching this one now (within a pixel and a half, as a settled pile jitters), nearest first, each with its tag, data (typed by ColliderData), owner, radius and where its centre is.
  • push(vx, vy) adds to its velocity in pixels per second (a blast); place(x, y) puts it somewhere at rest; speed() is how fast it moves, so a pile has settled when every ball is slow.
  • pin(true) holds it where it is: it does not fall, nothing pushes it, and other balls pile up on it as on something solid (a frozen fruit, a peg); pin(false) lets it go, from rest. The pinned option starts it held. setGravity(g) changes its gravity: 0 hangs it in the air, a negative one floats it up.
  • stick("fruit") sticks it to every ball with that tag touching it now, and it stays stuck: the two are held together, touching, and move as one lump (honey, a magnet, a string of beads). Call it every step to stick to whatever comes to touch it; it returns how many balls it is stuck to. unstick() lets go of them all, and a ball that leaves the world lets go by itself.
  • No bounce: piles settle rather than jitter. Balls that start overlapping (two made in one place) pop apart at no more than 300 pixels per second, not across the world.
  • The step is deterministic, and balls are solved in an order worked out from where they are, so rewind and replays reproduce a pile exactly. While the world is paused or frozen, balls do not move.
  • Balls touch balls and solids only: a collider does not see a ball. A component that should be hit by others draws a <Collider> at its ball's position, as a body's does. Shaped solid colliders count as their boxes.

Moving with plain functions

A useBody component and plain functions produce the same movement. Kite's running, falling and jumping written as a component with useBody (games/kite/src/Runner.tsx) puts the character on the same pixel every step as Kite's rules do, through walls, ceiling corners and pits (test/runner.test.ts). Choose by who else needs the movement. Use a component when only it does, and plain functions when something else must run it too, such as a search or a solver that plays a room thousands of times without a world.

Kite's plain movement functions read the same tile data as a <Tilemap>:

tileAt(layer, col, row)The global tile id (0 when empty or outside).

objects(type?)The map's objects (of one Class), with x, y, width, height, name and properties.

  • Reading outside the map gives an empty cell, not an error.
  • Kite puts gameplay data in a hidden layer (Markers: room start and exit tiles) and finds it with find("Markers", gid). Only the visible Tiles layer is drawn.
  • A map of any size costs what its view does: in the world, an unrotated, unscaled <Tilemap> writes only the cells the camera shows (and one more cell round them). Inside a <Hud>, or turned or scaled, it writes every cell.
  • A large map does not need splitting, but you can still mount part of it: Kite maps over its room list and mounts the current room and its neighbours.
  • moveActorX / moveActorY move { x, y, rx, ry } a pixel at a time against blocked(x, y), carrying the sub-pixel remainder. On a block the remainder is dropped and onBlocked(direction) runs; it may move the actor (a corner correction).
  • Tilesets can be embedded, or external as JSON (.tsj) or XML (.tsx). Without image, a <Tilemap> draws each tile from its own tileset's sheet, with its margin and spacing, so keep the sheets in the assets folder; a tile larger than a cell sits on the bottom of it, as in Tiled. With image, every tile is cut from that one sheet.
  • To use map objects as data, give an object layer the bool property data and its objects are for your rules, not prefabs: getTilemap("room1").objects("door") gives each one's position, size, name and custom properties, and the map's own properties are property(name). Bramble reads its doors, people, items and enemies this way (games/bramble/src/rules/maps.ts), checking each one and naming the map and object when something is wrong.
  • Importer limits: finite maps; CSV or base64 layers (uncompressed, zlib or gzip, not zstd); not tilesets that are collections of images. Each is reported when imported.

Scenes and prefabs

Every exported component is a prefab that JSON scenes can place by name.

  • Callbacks cannot come from data, and children is passed, not set.
  • Scene children mount after the prefab's own, or at its {children} slot.
  • Validate with tse-compile src out --scenes scenes (TSE1501–1509). Tiled .tmj maps are imported too.
  • Exported names must be unique across files (TSE1206).

How a frame works

  1. A new left click goes to the topmost Pointer / Flex onPress under the mouse.
  2. Each step runs world.tick(dt, input) (one step a frame, or as many as fixedStep holds): all useInput handlers, then all useUpdate handlers, then every dirty component renders once, then structural changes commit (conditions and list items mount and unmount).
  3. After each step, new touching pairs call onCollisionEnter and separated ones onCollisionExit. What they change renders at once, so the next step sees it and a run collides at the same steps at any frame rate.
  4. To draw, the tree is walked depth-first into draw records in tree order (or z order), with the camera applied. A contact and what it caused are drawn in the same frame.
  5. The backend draws and presents, then supplies next frame's input.

What follows from this order

  • A field written in a handler shows at the next render; the handler reads it back at once.
  • Components see each other's changes a step apart. Every update in a step sees the state as the step began, so a value a child reports to its parent in a step (onMove(x), then the parent's setPlayerX) reaches its siblings, by props or through context, in the next step. That is one step of lag between independent things, and it repeats exactly. Where it matters, a built-in reads its child directly, as <Camera> follows what it holds.
  • Objects attached mid-frame get hooks next frame.
  • With fixedStep, steps 2 to 4 above run once per whole step, and drawing runs once per frame. See Input and timing.
  • freeze(n) skips useUpdate (not useInput or renders) for n steps.
  • Any number of state writes in a frame means one render. AnimatedSprite costs no renders.
  • Unchanged subtrees reuse last frame's draw records.
  • Bad assets never crash: a missing image or unreadable colour draws magenta, with one warning.
  • Colours are CSS: #rgb, #rgba, #rrggbb, #rrggbbaa, rgb(), rgba(), named colours, transparent.
