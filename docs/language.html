tseAuthoring guide and reference

Components

A component is a top-level function or const arrow with a capitalised name, optionally exported (one per module may be the default, and it needs a name). Its body, in order:

  1. Hooks: useMutable, useSound, useGame(...), and the handler hooks.
  2. Derived values: const hurt = health < 25;, and destructured ones, const { x, y } = heroOf(run); or const [a, , c] = trio; (plain names: no defaults, rests or nesting). One that calls a function or a method is worked out once and again only when the state or props it reads change, as with useMemo; one that only combines values is written where it is used.
  3. What a render does: it compares each state field, prop and game-state value the component's elements read with what it was at the last render (===), and works out and writes only the values of the elements that read one that changed. An enemy that moves every step rewrites its position, not its sprite's tint or its health bar's props. So there is no useMemo, useCallback or React.memo to write: the compiler sees what each value reads. A value changes when it is a different value. A useMutable field changed in place (s.items.push(item)) is written for you as a new value (see useMutable); a prop's object or the game state is changed by making a new one, never in place, as in React. What is under a condition or in a list is worked out on every render, and so is a value that calls one of the component's own functions or a callback prop, whose reads the compiler does not follow.
  4. One return of JSX, a condition of it (on ? <Spark /> : null, open && <Menu />) or null.

An arrow with an expression body returns that expression: const Dot = () => <Sprite image="dot.png" />.

Beside the components, a file may hold constants and helper functions, as a React file does: const ROW = { bolt: 0, frost: 2 } as const;, function labelOf(kind: Kind) { … }. Render expressions may index them (ROW[kind] * 3) and use Math.PI. A top-level let, or a constant holding JSX or reading the game state, is TSE1001.

The root

The root (or a fragment <>…</>, an implicit Entity) is usually a built-in. The class extends it, so the root's props apply to the component itself. The root may also be another component (return <Panel title="BUILD">…</Panel>), a condition or null: the component is then a bare container that <Flex> layout sees through, so a panel it returns still grows to the column it sits in.

A root <Entity>, <Game> or fragment with no name is named after the component: function Player() returning <Entity> is <Entity name="Player">, which is what a collision's other.owner reads. Write name only to say something else (an id, in a list). Nested entities are not named for you.

State and props may use any name, including one the root built-in has: a useMutable called name on an Entity root, a width on a Collider root. The compiler keeps such a state in a field of its own ($name), so the entity's own name is untouched.

Imports

  • Hooks, elements, clamp and the Child type: from "@tsengine/runtime/jsx" (import { type Child }).
  • Components: from "./Name.tsx", named or default. No namespace imports or as.
  • Game state: useGame from "./GameState.ts". Other relative .ts imports are plain functions and constants (see below), by name or whole (import * as K from "./constants.ts", read as K.SPEED and called as K.statsOf(…)); relative .tsx imports are components or custom hooks.
  • Imports are mandatory: an unimported hook or element is TSE1005.
  • Math needs no import.

Allowed in a component body

Allowed
  • Number, string, boolean, null and undefined (gate !== undefined)
  • State and prop reads
  • Unary ! - +, binary arithmetic, comparison, logical
  • a ? b : c, parentheses, template literals
  • Array and object literals, with spreads
  • Member reads (e.id, items.length, found?.hp)
  • Non-mutating array methods (map, filter, some, flatMap, join, at…), and reduce, and the copying forms toSorted, toReversed, toSpliced, with, findLast. sort and reverse on an array made right there ([...list].sort(byX), list.filter(f).reverse()) sort a copy, so they are written as toSorted and toReversed
  • Methods of strings and numbers that change nothing (padStart, startsWith, slice, toUpperCase, split, replace, toFixed…), and String(n), Number(s), Boolean(x)
  • Calling a function from a relative .ts file or the same file (spotsOf(run)): assumed pure
  • Statements that compute: let, loops, if, a list built up with push, new Map(), as a handler may. A run of them is worked out together, and again only when what it reads changes; the names it declares (const or let, one name each) are values after it:
    They run during render, so they cannot write state, play a sound, call an action or return early.
  • Functions, declared as React code declares its handlers: const add = (n: number) => { s.points += n; };. Such a function is one of the component's handlers: call it in a handler or a callback (useUpdate(() => add(1))), pass it to an element (onPress={press}), to a child or to a hook. It is not called while rendering, since it may write state.
Not allowed
  • Anywhere: var, await, this
  • Methods that change a prop in place, or a state value outside a useMutable field (push, sort… on them): build a new value; on a list a block or handler made itself, and on a field of a useMutable, they are fine
  • Text children and spread attributes in JSX
  • useEffect, ref={…}
  • Hooks inside conditions, loops or handlers
  • Passing the bare props object on or spreading it

useMutable

A component's state: an object of fields you write directly. Each field renders when it changes, is saved, and is kept by hot reload and rewind. A handler reads its own writes at once, so a step needs no local copies and no setters; render sees what the frame committed. It replaces React's useState: a useState is TSE1102, whose message writes out the conversion in your names.

  • Form: const s = useMutable({ a: 0, b: false }), one object literal of plain name: value fields (TSE1103). A literal of numbers, strings and booleans (and objects and non-empty arrays of them) gets the type TypeScript would infer; an empty array, or a value whose type cannot be read from it, takes its type with as (spawns: [] as Spawn[], the type declared in the same file), else TSE1104.
  • The initial values are taken when the component is made: a constant, a prop, a value of the game state, or a field of a useMutable declared above it, as in React's first render. A per-instance object with methods may be a field (body: createBody(options)), its methods called through it (s.body.move(1, 0)).
  • A handler and render see a field at different moments. A handler (useUpdate, useInput, a callback prop, a function in the body) sees a field as it was last written, this step included, and so do later handlers in the same step. Render, and the elements and props it makes, see what the step committed. A derived const that reads a field follows the same rule: in a handler it is worked out from the fields as they are now. So does a prop: a handler reads health as the parent has it now, which includes what a component before it in the tree wrote this step (parents first, then siblings in order). Children made in a list (found again by key), the components below a list item, an item that switches between two elements, and one made with a key read their props live the same way, and so does a value passed by context. Only a callback prop is not live: it is a function, made once.
  • Fields are written in handlers only: =, +=, -=, *=, /=, %=, ||=, &&=, ??=, ++, --. Not in the component body (TSE1402) or in useUnmount. A write of the same value (===) renders nothing.
  • A list or object field can be changed in place. s.list.push(x), pop, shift, unshift, splice, sort, reverse (each a statement of its own), s.list[i].hp -= 1, s.pos.x = 3 and s.list[i].tags.push(t) are written for you as the new value the field would be given (s.list = [...s.list, x], s.list.with(i, { ...s.list[i], hp: … })), so only what the path passes through is copied, and render and other components compare values as before. A handler reads the change back at once. Not supported, with a message that says what to write: a result used as a value (const n = s.list.push(x)), an index that is not a plain value (s.list[next()]), ?., and a change through another name (const e = s.list[0]; e.hp = 0, or a loop over a copy, for (const e of s.list.filter(…)) e.hp = 0): write s.list = s.list.map(…) there. A loop over the field itself may write through its item: for (const e of s.list) { e.hp -= 1; } is written as a loop over the index, each write s.list[i].hp -= 1, and a read of e after it sees the change. Such a loop cannot also change the list itself (push, splice, a new s.list): change the items in the loop and the list after it. Each write copies the list, so for hundreds of items, build the new list with map and assign it once. An index write needs an array; a record is replaced with a spread.
  • A list field is a MutableList<T>: the forms above type-check, but it is not assignable to T[], so a helper that takes Foe[] and changes it in place is an error. Take readonly Foe[] to read a list, or return the new one.
  • In a handler, s passed whole is the component's own object for that useMutable, made the first time a handler passes it and kept for the component's life: a helper that writes it changes the component's fields, and the handler reads them back at once, as if it had written s.hp -= 3 itself.

    In render (an element's props, <Camera shake={shake}>, {label(s)}) it is a copy of the fields as the frame committed them, typed Readonly: render writes nothing. A list field of the object is still a MutableList, so a helper that changes it in place is an error (as above); a helper gives the field a new list (target.foes = [...target.foes, foe]). A write through the object after the component is unmounted (a helper that kept it) does nothing and warns once in development. const t = s is another name for the same fields, and a custom hook hands its state back with return s: the caller writes counter.n += 1.
  • A callback under a condition on a field ({s.waiting !== null && <Prompt onKey={…} />}) reads a const waiting = s.waiting taken above, as TypeScript keeps a const's narrowing inside a closure and not a field's.
  • In a test, t.state().s.vx reads a field; on a compiled component, component.s.vx reads it and component.s.vx = 1 writes it.

A value that never renders

There is no useRef: like useState, it is TSE1102, and its message writes out the conversion. A timer, an accumulator or a previous value is a useMutable field that the JSX does not read. A write marks the component, but a render only redoes the parts that read a changed field, so a field nothing reads changes nothing that is drawn.

A field cannot be written in useUnmount: the component is going away. Tell the parent with a callback prop.

Input is polled each frame. There are no key-event props.

Key names (an unknown name warns once and never fires):

useUpdate

dt is the time in seconds (frame time clamped to between 0 and 0.1, or the fixed step under fixedStep). Multiply speeds by it. A second argument is the same input that useInput gets: useUpdate((dt, input) => step(input, dt)).

useInput or useUpdate? Something that happens once, on a press (open the menu, pause, fire) goes in useInput. Something that happens over time (move while a key is held, step the rules) goes in useUpdate((dt, input) => …), which reads the keys itself. Both get the same input in the same step, so do not copy keys into a field to carry them from one hook to the other.

Each handler hook may appear several times; they run in source order.

useMount / useUnmount

  • Mounts when attached to the world (a condition turns on, a list item is added); unmounts when detached.
  • Each takes one arrow function with no parameters.
  • No useEffect (see below), but useMount may return a cleanup, as an effect does in React.

A cleanup from useMount

  • A function returned from useMount runs once, when the component leaves the world, after its useUnmount handlers. Anything else returned is ignored. An expression body's call is returned, as in React (() => listen(…)).
  • In any handler, an arrow may be handed to a plain function, a method of an imported object, a callback prop or a local (settings.subscribe(() => …)). It is a handler of its own: it may write state and call actions. Outside a handler, an arrow cannot be handed on.
  • A hot reload removes the old tree, so its cleanups run and the new tree subscribes again.

No useEffect: what to write instead

There is no useEffect, on purpose. Here an effect would run a frame after the change it answers (and a frame more for each effect it sets off), and it would pull game logic out of the rules, which are plain functions you can test and replay without a window. Each job an effect does in React is done another way here:

You wantWrite
A sound, a burst or a shake when something happensDo it where it happens: the rules return events, a game-state action answers them through effect stores (sfx.play("hit"), fx.burst(…)). See Effects.
A value computed from state or propsA derived const: worked out again when what it reads changes.
Music, an emitter or the camera to follow stateA built-in with props: <Music>, <Particles emitting>, <Camera bounds>.
Something when the component comes or goesuseMount / useUnmount.
To subscribe to something outside the game stateSubscribe in useMount and return what stops it: useMount(() => settings.subscribe(() => …)). See the cleanup.
To start a component's state over when what it shows changesA key on the element, as in React: <Dialogue key={talk.id} />. See keyed elements.

Writing useEffect is TSE1102, and the message points here. The reasons in full are in docs/DESIGN.md, “Why there is no useEffect”.

useSound

Call it as a statement in a handler (elsewhere is TSE1305); playHit(0.5) plays at half volume. A sound played again while sounding overlaps itself, up to four at once. Paths are relative to <Game assets>. Sounds preload.

What handler code may contain

Handlers (hook bodies and callback props) may contain:

Statements
  • if / else, early return
  • const locals
  • Writing a field: s.x = 5, s.x += 1, s.x++ (and %=, **=, ??=, ||=, &&=)
  • let locals, optionally typed (let best: Enemy | null = null), assigned the same ways
  • for (const e of enemies) { … }, destructuring too: for (const [i, { id }] of enemies.entries())
  • for (let i = 0; i < n; i++), while and do…while, all with break and continue
  • try / catch / finally and throw
  • switch (falling through as in JS) and { … } blocks
  • Calling a sound function or a useGame action (const events = step(input, dt) may use its result)
  • Calling a plain function, or a method of an imported object (fx.burst(…))
  • Calling a callback prop: onDone?.(), or a local holding a function: stop()
  • Handing an arrow to any of those: settings.subscribe(() => { s.view = read(); })
  • In useMount only, returning a cleanup: return () => stop();
Calls and members
  • Math.abs floor ceil round sign sqrt sin cos min max
  • The array, string and number methods allowed in a component body (id.startsWith("bind:"), id.slice(5))
  • clamp(value, min, max) (3 args)
  • freeze(steps): skip every useUpdate for that many steps
  • input.pressed / down / released, input.pointerX / pointerY
  • A value the handler made itself (an array or object literal, new, or what a call returns): any method (list.push(e), seen.add(id), best.sort((a, b) => a.hp - b.hp)) and assignment into it (tally.hits++, grid[y]![x] = 1). A local that only reads state or a prop (const list = enemies, enemies.find(…)) is not the handler's: state is changed with its setter.
  • new of Map, Set, WeakMap, WeakSet, Array, the Error types, or a class imported from a .ts file (not Date: it reads the clock)
  • The standard library as written: Object.*, JSON.*, Number.*, Array.*, String.*, any Math function, console.*, parseInt, parseFloat, isNaN, isFinite. Math.random() warns: replays and tests will not repeat it.
  • typeof, instanceof and in, which also work in a component body
  • other.tag, other.owner in collision callbacks
  • Template literals

A function's parameters are plain names, typed or not. One may be optional, (step?: number) => …, and stays optional in the generated function; a default (step = 1) or a rest parameter is not taken, so give the default in the body: step ?? 1.

A component has no as: a cast overrides the type-checker, so it goes in a function in a .ts module, where it is easy to find and to test, and the component calls that. table[key]! is kept as written and value satisfies Point keeps the value alone. (The one as a component writes is the type of a useMutable field, spawns: [] as Spawn[].)

Anything else (var, a labelled break, assigning to anything but a useMutable field or a let) is TSE1301, TSE1401 or TSE1402.

Custom hooks and plain functions

Logic you would extract in React, you extract here: into a custom hook (state and handlers, reused) or a plain function in a .ts file (a calculation, a table).

Custom hooks

A function named use… whose body is what a component body may hold is a custom hook. A call to it as a statement of a component body is replaced by the hook's own statements before compiling, so every rule still applies.

  • Each call gets its own state, so two calls make two separate states.
  • An argument that is a literal or an import is written into the hook (so it can be a useSound path, or a store the hook subscribes to); any other argument is bound to a const, so it is worked out once. Defaults work, and so does a destructured parameter, function useMover({ speed, limit }: Options).
  • A hook may take a function and call it in a handler: useEvery(1, () => { s.ticks += 1; }). The arrow becomes a function of the component (see below).
  • A caller takes what a hook returns as const v = useX(), const {a, b} = useX() (object literal), const [a, b] = useX() (array literal). A name the hook returns as it is takes the caller's name, so a hook can return its useMutable (return s;) and the caller reads and writes its fields.
  • A hook is inlined, not called: each call's statements are written into the component. That is why each call has its own state, and why a hook cannot be called in a condition or a loop (the same rule as React, for another reason), nor call itself.
  • A hook is declared in the same file or imported from a relative .tsx. Hooks may call hooks, up to six deep.
  • A call anywhere but a statement of the component body is TSE1101.

Hooks the engine ships

These are ordinary custom hooks, imported from @tsengine/runtime/jsx.

useStore(store, read) takes anything with subscribe(listener) that returns a stop function (createSettings stores, controls, a store of your own) and a function of no arguments that returns what to show, both imported from .ts files. It renders only when the data read returns differs (keepIfEqual, which a handler can call too).

useInputDevice() says what the player is using, so a prompt can be worded for it: device === "keyboard" ? "Press Enter" : "Tap to start". A mouse and a finger are both "pointer": a touch is a left click to a game. It is "pointer" until something is pressed, so a game on a phone never names a key, and the component renders only when it changes. Outside a component, getInputDevice() reads the same value.

useWindowSize() is the window's size in logical pixels (a phone's points), so a landscape game can ask a phone held upright to be turned: window.height > window.width && <RotatePrompt />. It is the window, not the game's resolution: a <Screen> is still scaled into it as its fit says. The component renders only when the size changes. Outside a component, getWindowSize() reads the same value, and a test can set it with setWindowSize(width, height).

Plain functions and constants

Import functions and constants from a relative .ts file and use them in any expression: a prop, a derived value, a handler. You can also pass a function as a value. The compiler does not look inside: TypeScript checks the call, and the function is assumed pure. Loops, arrays and anything else are fine in its body.

This is how Kite, the platformer in games/kite, is built, and why: a solver proves each room can be finished by stepping the character thousands of times from copied states, which plain functions make cheap. For anything else, keep the game in components (Hearth's enemies and towers), which @tsengine/testing tests as easily as a function.

  • The name must not start with use.
  • A dynamic prop that calls a function re-evaluates when the state in its arguments changes.
  • A handler may keep the result of a plain function or a useGame action in a const and use it. In JSX or a derived value, a call would run on every render.
  • Nothing re-renders when code changes an imported constant. That suits data and effect stores, not game state (use useGame).
  • You can call methods of imported objects (fx.burst(…)) in handlers and expressions. An array method on an imported array (ROOMS.filter) is still lowered, so its callback may read state.

Position and drawing order

Every built-in except Game, Screen, Router, Route, Fade and Music takes these props. All are optional and may come from state.

PropDefaultMeaning
x, y0Pixels, relative to the parent. y points down.
rotation0Radians. Positive turns clockwise.
scaleX, scaleY1Per-axis scale. Negative flips.
z0Draw order: higher is drawn later, so on top. Negative is behind. It adds to the parent's, so raising a component raises everything in it.
globalfalseTrue (global alone, or global={pinned}): the element is placed in world space and ignores the parent.

Opacity is a prop on every element too: <Entity opacity={fade}>, <Shape opacity={0.5} … />, <Sprite opacity={…} … />. It is 0 to 1 and fades the element and everything inside it, so an <Entity> fades a whole popup or card at once. It multiplies down the tree (0.5 inside 0.5 is 0.25), and each thing is drawn at it on its own, so where two overlap the one below shows through. To fade a component, wrap it: <Entity opacity={…}><Card /></Entity>; on the component itself opacity is whatever its own props say.

  • The origin is the top-left corner of a Sprite, AnimatedSprite, Shape, Text, Collider, Pointer; rotation and scale are about it.
  • Children are relative: x: 10 inside a parent at x: 100 is at 110, and turns and scales with the parent.
  • Equal z keeps tree order, globally across the tree.
  • A component takes none of these: on a component, x is whatever its props say. Place one by wrapping it, <Entity x={40} y={8}><Coin /></Entity>, or give it x and y props and put them on its root, as Hearth's Pad does.
  • There is no transform attribute: transform={{ … }} is TSE1207, whose message says what to write.

Props, callbacks and children

Props come through a destructured parameter typed with a props type written in the parameter (({ hp }: { hp: number }), which is then called HeartProps for a Heart) or declared in the same file (({ hp }: HeartProps)). A changed value updates the child in place; it is never recreated.

  • props: EnemyProps also works (props.speed), but props cannot be passed on or spread. Defaults go in the destructuring.
  • A prop may be read under another name, as in React: ({ seed: firstSeed, speed: rate = 2 }: EnemyProps), so a prop and the state it seeds can both be called what they are.
  • Callback props carry messages from child to parent. Call optional ones with ?.(). Whether one was passed may be tested: onAdjust === undefined, or by its truth in a choice (below).
  • A callback attribute may be a choice: onPress={open ? close : undefined}. Each branch is an arrow, a function passed whole (a callback prop, a function of the component's, an action) or undefined, and the choice is made again when what its condition reads changes. While the branch taken is undefined a built-in has no handler, so the box does not take the press or the mouse; the same goes for <Flex onPress={onPress}> when onPress was not passed. A branch whose test proves a callback prop was passed may call it: onPress === undefined ? undefined : () => onPress(). To a component, each branch is passed whole: declare the arrow in the body (const go = (n: number) => …) and write onGo={open ? go : undefined}.
  • A bad props form is TSE1208.

Passing children

Declare children: Child and place {children} once, directly inside a container (the root, a fragment, or a static <Entity>). The parent owns what it passes and updates it from its own state.

A component can build on another and pass its {children} on, between children of its own; and what a parent passes may mix single elements, conditions and a list. Each keeps the place it was written in, as items come, go and move.

Text wrappers

A component that writes text in one style takes its words as children, as <Text> does: declare children: TextChild | readonly TextChild[] and pass them on with <Text>{children}</Text>.

  • The words become one string, passed as the children prop: a change of coins renders the text again, nothing else.
  • A text wrapper may pass its words on to another (<Button> holding a <Label>{children}</Label>).
  • A component takes text or elements, never both at once: children: Child is for elements.
  • When the whole game writes in one size and colour, set them once at the root instead: <Game textSize={10} textColor="#e8d9a8">. Every <Text> without its own size or color uses them. They are not inherited from containers: a text's look never depends on where it is in the tree.

Conditions and lists

JSX children are elements, conditionals or keyed lists. Anything else (text, other expressions) is TSE1202, except text inside <Text> and inside a text wrapper.

A list's callback takes the item and, if wanted, its index: (item, index) =>. The item may be taken apart into plain members, ({ id, x }) => or ({ id: n }) =>, with no default, rest or nested pattern.

A list can sit under a condition: {show && items.map((item) => <Row key={item.id} />)}.

Conditionals

A condition turning off unmounts the child; turning on mounts it. To switch several siblings on one condition, wrap them in a fragment: {gems === 0 && (<><Shape … /><Collider … /></>)}.

Keyed lists

Rule (otherwise TSE1209)
The items are any array the component can compute: state or a prop, a member of one (world.enemies), an array method's result (.filter, .map, .slice), an imported constant, or what a plain function returns (spotsOf(run)). The list follows the state and props the expression reads. Not through ?..
map takes one inline arrow (item, optionally index) returning one element, cond && <El key … /> or cond ? <A key … /> : <B key … />: an expression body, or a block with only return. No fragments.
The element may have children, nested and conditional ({slot.filled && <Text … />}), that read the item, and lists of its own ({row.cells.map(…)}), nested as deep as needed. They cannot include {children} or a <Route>; for those, make the item a component.
The element has a key that reads the item (key={e.id}). A key reading only the index compiles with a warning; one reading neither is an error.
A callback on the item may read the item but not the index; one in a nested list may read the items around it too.

Instances follow keys, so each keeps its own state as items move. A computed list is worked out once per render of the component, which happens when what it reads changes.

Keyed elements

A key on an element outside a list starts it over when the key changes, as in React: the old instance unmounts and a new one mounts, with fresh state. While the key stays the same, a changed prop updates it in place, as usual.

  • The key is any value that identifies what the element shows (a string or a number), and may read state and props.
  • The new instance is added before the old one is removed, as with list items, so its useMount runs before the old one's useUnmount.
  • Not on a component's root (TSE1203): put the key where the component is used. Not inside a list item's children (TSE1209): make the item a component. Beside other children passed to a component it is fine.

Game state: createGameState

The game state is what every component shares (score, hit points): its data and the actions that change it. A component reads with a selector and calls actions; only actions change it.

Rules

  • A selector is a path (s.stats.coins) to a leaf, an object or an array, or any expression of paths ((s) => s.cursor === id, (s) => focusOf(s.battle, s.cursor)): each path it reads is subscribed to, and the value is worked out again when one changes. A typo is TSE1108. Call useGame(...) at the top level, bound to a const, or destructured: const { room, deaths } = useGame((s) => s.run).
  • Actions come from const { collect, hurt } = useGame.actions(). They never change, so this subscribes to nothing. A name there that is a value of the state, or a typo, is TSE1108; taking actions from the whole state (useGame((s) => s)) still works but warns. In plain code, useGame.actions().collect().
  • An action may be passed whole: onPress={resume}.
  • Call an action as a statement in a handler, not in JSX or a derived value.
  • An action writes the state directly, nested objects and lists too (s.run.time += dt, s.gems.push(id)). It writes a draft; when it returns, only the values that changed are committed, and only their readers hear of it. An action called from another shares its draft. One that throws changes nothing.
  • Only components reading something that changed re-render. Every game starts from the initial state.
  • The data must be an object literal: number, string and boolean literals, nested objects, and other values (arrays, newRun()) kept as values; no functions. The actions are an object literal of functions. Spreads, computed keys and a name in both are TSE1109.
  • What a selector returns is read-only, deep: run.time = 0 or items.push(x) in a component is TSE1402 / TSE1301, whose message names the action to add, and a helper that takes a mutable Item[] is a type error for a selected list (take readonly Item[]).
  • An action may call another (useGame.actions().begin()), and plain code it calls (a save's pick) reads what it has written so far through useGame.getState().
  • useGame.getState() reads the state outside components. useGame.setState({ … }) replaces part of it (shallow-merged) for tests, a story's setup and tools; game code uses actions, and setState while an action runs is an error.
  • The Zustand form, createGameState<State>()((set) => ({ … })), is not supported: TSE1109 says what to write instead.

Kite keeps screen: "title" | "play" | "end" in the game state and gives it to <Router route={screen}>, so any action (begin, finished) changes screens. Actions are plain TypeScript: they can call a sound store (sfx.play("start")) as well as write the state.

useMutable, context or useGame? useMutable for what one component owns; context for what a component shares with everything below it; useGame for what the whole game shares.

Sharing state between components

As in React, what two components need lives in their nearest common parent, so you lift it up. The parent keeps it in useMutable, a child reports to it through a callback prop, and the parent hands it down as a prop, or through context to a deep subtree. The game state is the top of that ladder, for what the whole game shares (the screen, the score).

A handler reads a prop or a context value as the parent has it now: an enemy after the player in the tree sees where the player moved this step, one before it sees where it was when the step began. The order is the tree's, parents first, the same on every run (see How a frame works). Render shows what the step committed.

Context

Context works as in React: a component provides a value to everything below it, and a component reads it where it is needed instead of having it passed down through every level.

  • useContext reads the nearest provider of that context above the component, or the context's default when there is none. The component renders again when that provider's value changes.
  • A provider is a container that layout sees through and that draws nothing. It is written <Theme.Provider value> and compiled into the built-in <Provider context={Theme} value>.
  • The context is made once, in a .ts file, and imported. A component finds its provider when it joins the world; components are never moved, so it keeps it.
